# KnowFlow 技术亮点详解

本文档说明 KnowFlow 当前实现中的核心技术亮点。每个亮点都对应真实代码模块，并能通过 API 或 Docker 环境观察到效果。

KnowFlow 是企业级知识库 RAG 问答系统，已上线生产环境（know-flow.dev），支持真实用户注册、文档上传、流式问答和管理后台。这不是 Demo——392 个测试用例、Alembic 数据库迁移、JWT 认证权限体系、Docker 全栈部署，构成了一个可交付的生产系统。

当前版本重点实现：

| 能力 | 关键代码 | 可观察入口 |
|------|----------|------------|
| 双路检索 + RRF 融合 + 精排 | `services/retrieval.py`、`services/reranker.py` | `/chat` 响应中的 `sources` |
| 结构感知文档分块 | `pipeline/chunker.py` | 文档上传后 `/documents` 查看 chunks |
| LLM 查询改写 | `services/rewriter.py` | 后端日志 `查询改写:` |
| SSE 流式生成 + JSON 边界检测 | `services/chat.py`、`api/v1/chat.py` | `/chat` 实时打字效果 |
| Celery 异步索引 + 失败重试 | `tasks/indexing.py`、`core/celery.py` | 文档状态从 processing→indexed |
| JWT 认证 + 多层权限 | `core/security.py`、`services/retrieval.py` | 非管理员只能检索授权文档 |
| LangGraph Agent 编排 | `agent_runtime/` | `/agents/sessions/{id}/messages` |

## 总体架构

```text
用户请求
  -> nginx (SSL) -> frontend (Next.js 15) + backend (FastAPI)
  -> backend:
       -> JWT 认证 (core/security.py)
       -> 查询改写 (services/rewriter.py)
       -> 双路检索 (services/retrieval.py)
            ├── 向量检索 (pgvector cosine)
            ├── BM25 全文检索 (tsvector + jieba 分词)
            ├── RRF 融合
            ├── LIKE 子串补充 (中文人名兜底)
            └── Reranker 精排 (bge-reranker-base)
       -> LLM 流式生成 (litellm + SSE)
       -> 消息持久化 (PostgreSQL)

文档上传
  -> backend 接收 -> Celery 异步任务
  -> 文本提取 -> 结构感知分块 -> Embedding -> pgvector 存储
  -> 同时构建 tsvector 全文索引
  -> 失败自动重试 3 次 + beat 每小时扫描恢复
```

## 亮点一：双路混合检索 + RRF 融合

**文件**：`backend/app/services/retrieval.py`

**核心问题**：企业知识库检索既要理解语义（"请假怎么请"匹配到"年假申请流程"），又要精确匹配关键词（搜索员工姓名"赵六"必须命中）。单路向量检索擅长语义但漏掉精确匹配，单路 BM25 擅长关键词但无法理解同义表达。

### 技术方案

```text
用户查询
    ↓
查询改写（LLM 解析代词指代、补充专有名词）
    ↓
┌─────────────────────────────────────────┐
│ 并行双路召回                              │
│                                          │
│ 路径A: 向量检索 (pgvector)               │
│  - cosine 距离 1-(embedding<=>query)     │
│  - 语义相似，"请假"→"年假"能匹配          │
│  - 取 top_k * 2 条                       │
│                                          │
│ 路径B: BM25 全文检索 (tsvector)           │
│  - jieba 分词 + 停用词过滤                │
│  - ts_rank 精确匹配关键词                 │
│  - 取 top_k * 2 条                       │
└─────────────────────────────────────────┘
    ↓
RRF 融合 (Reciprocal Rank Fusion)
  score = Σ 1/(k + rank_i),  k=60
  无需调参，两路结果按排名倒数加权求和
    ↓
去重（同一文档最多保留 2 个 chunk）
    ↓
LIKE 子串补充
  提取查询中的 CJK 连续片段（如人名"赵六"）
  ILIKE 模糊匹配，补回向量/BM25 都漏掉的结果
    ↓
Reranker 精排 (bge-reranker-base)
  对 query-chunk 对打分，重新排序，取最终 top_k
```

### 为什么用 RRF 而不是加权分数

| 方案 | 问题 |
|------|------|
| 加权分数 `0.5*vec + 0.5*bm25` | 两路分数量纲不同（cosine 0-1，ts_rank 0-∞），权重难调 |
| 归一化后加权 | 归一化方法敏感，不同 query 分布不同 |
| **RRF** | 只用排名不用分数，天然消除量纲差异，k=60 是论文推荐值，无需调参 |

### 向量检索的权限过滤

非管理员查询时，SQL 会拼接权限子句：

```sql
AND (
    EXISTS (SELECT 1 FROM document_permissions dp
            WHERE dp.document_id = d.id AND dp.user_id = :uid)
    OR EXISTS (SELECT 1 FROM source_permissions sp
               WHERE sp.source_id = d.source_id AND sp.user_id = :uid)
    OR EXISTS (SELECT 1 FROM knowledge_base_members kbm
               WHERE kbm.kb_id = d.kb_id AND kbm.user_id = :uid)
)
```

三层权限：文档级 → 数据源级 → 知识库级，任一命中即可访问。这保证企业数据隔离——用户只能检索到自己有权限的文档。

### BM25 的中文分词

PostgreSQL 原生 `to_tsvector('simple', ...)` 不分词，中文整句作为一个 token，导致 BM25 对中文几乎失效。KnowFlow 的解法：

```python
# indexer.py — 索引时
import jieba
words = jieba.cut_for_search(content)
tsvector_str = " ".join(words)  # 空格分词后存入 tsvector

# retrieval.py — 查询时同样 jieba 分词
tokens = _tokenize(query)  # jieba + 停用词过滤
tsquery_str = " | ".join(tokens)  # OR 查询
```

索引和查询用同一套分词器，保证一致性。中文单字保留（人名"赵六"分词后可能是"赵""六"）。

### 降级策略

| 场景 | 降级方式 |
|------|---------|
| Embedding 服务不可用（401/超时） | 向量检索返回空，只用 BM25 + LIKE |
| Reranker 未安装 | 按 RRF 分数降序取 top_k |
| 单路召回为空 | RRF 仍可用另一路结果 |

## 亮点二：结构感知文档分块

**文件**：`backend/app/pipeline/chunker.py`

**核心问题**：文档分块是 RAG 的基础——块太大检索不精准，块太小丢失上下文。固定长度切割会破坏 Markdown 标题、代码块、表格的语义完整性。

### 技术方案

```text
原始文档
    ↓
1. 代码块隔离
   用 UUID 占位符替换 ```...``` 块，避免后续切割破坏
    ↓
2. Markdown 标题分割
   按 #{1-4} 标题 和 "章节标题：" 模式分割为 sections
    ↓
3. 逐 section 判断
   - section + 当前块 ≤ chunk_size → 追加
   - section + 当前块 > chunk_size → flush 当前块，保留尾部 overlap
   - 单 section > chunk_size → 段落级语义切分（按 \n\n）
    ↓
4. 还原代码块
   占位符替换回原始代码块内容
    ↓
输出: [{content, metadata, index}, ...]
```

### 三个关键设计

**代码块保护**：很多技术文档含 SQL/Python 代码，固定长度切割会把一个完整函数切成两半。先用占位符隔离，切完再还原。

**滑动窗口 overlap**：块之间保留 64 字符重叠（默认 chunk_size=512），保证跨块语义连续——一个概念出现在块尾，下个块头也有，检索时两个块都能命中。

**段落级兜底**：没有 Markdown 结构的长文本（纯 TXT），按 `\n\n` 段落边界切分，而不是暴力按字符数切割。

### 默认参数

| 参数 | 值 | 说明 |
|------|-----|------|
| `CHUNK_SIZE` | 512 token | 单块最大长度 |
| `CHUNK_OVERLAP` | 64 token | 块间重叠 |

## 亮点三：SSE 流式生成 + JSON 边界检测

**文件**：`backend/app/services/chat.py`、`backend/app/api/v1/chat.py`

**核心问题**：RAG 系统的 LLM 回复需要流式输出（用户体验），但 prompt 要求 LLM 在末尾输出结构化 JSON（含 answer/sources/confidence）。如果直接流式，JSON 片段会显示给用户；如果等 JSON 完整再返回，又失去了流式效果。

### 技术方案

```text
LLM 流式输出 token
    ↓
逐 token 累积到 full_response
    ↓
检测 JSON 边界:
  - 出现 "```json" → 代码块式 JSON 开始
  - 出现 \n{ 模式 → 裸 JSON 开始
    ↓
边界前: 正常 yield token 给前端（用户可见）
边界后: 只累积不 yield（JSON 隐藏，后端解析）
    ↓
流结束后:
  - parse_rag_response(full_response) 提取 answer/sources/confidence
  - answer 已通过流式展示
  - sources 通过单独的 SSE event 推送
  - confidence 用于后端日志
```

### SSE 事件协议

前端通过 `data: ` 前缀解析三种事件：

```text
data: {"type": "sources", "data": [...]}    ← 检索结果（生成前推送）
data: {"type": "token", "data": "你好"}      ← 流式文本
data: {"type": "done"}                        ← 生成结束
data: {"type": "error", "data": "错误信息"}   ← 异常
```

### nginx SSE 配置

生产环境通过 nginx 反向代理，默认会缓冲响应导致 SSE 失效。必须显式关闭：

```nginx
location /api/ {
    proxy_buffering off;       # 关闭缓冲
    proxy_cache off;           # 关闭缓存
    proxy_set_header Connection '';
    proxy_http_version 1.1;
    chunked_transfer_encoding off;
}
```

后端响应头也要加 `X-Accel-Buffering: no`，双保险。

## 亮点四：Celery 异步索引 + 失败重试闭环

**文件**：`backend/app/tasks/indexing.py`、`backend/app/core/celery.py`

**核心问题**：文档上传后需要文本提取→分块→Embedding→存储，耗时数秒到数十秒。同步处理会阻塞 API，异步处理又引入了"索引失败怎么办"的新问题。

### 技术方案

```text
文档上传 (POST /documents/upload)
    ↓
立即返回 200（status=pending）
    ↓
Celery 异步任务 index_document_task
    ↓
┌─────────────────────────────────────────────┐
│ _index_with_lock(document_id)                │
│  1. Redis 幂等锁（防止重复索引）              │
│  2. status → processing                      │
│  3. chunker.chunk(content)                    │
│  4. embedding_service.embed(chunks)           │
│  5. 写入 document_chunks（向量 + tsvector）   │
│  6. status → indexed                          │
│  7. webhook 通知 document.indexed             │
└─────────────────────────────────────────────┘
    ↓ 失败时
异常 re-raise → Celery 自动重试 3 次（间隔 60s）
    ↓ 重试用完
status → failed, error_message 记录原因
    ↓
Celery Beat 每小时扫描 failed 文档
retry_count < 3 的自动重新入队
```

### 三层容错

| 层级 | 机制 | 代码位置 |
|------|------|---------|
| L1 瞬时故障 | Celery `self.retry(exc=e, countdown=60)`，自动重试 3 次 | `indexing.py` |
| L2 持久故障 | Beat 定时任务 `retry_failed_documents`，每小时扫描恢复 | `celery.py` beat_schedule |
| L3 状态安全 | 即使 commit 失败也回滚重写 status，绝不卡在 processing | `indexing.py` 异常处理 |

### 幂等锁

用 Redis `SET NX EX` 实现分布式锁，防止同一文档被并发索引两次。释放时用 Lua 脚本验证 token，防止误删别人的锁。

```python
_RELEASE_LUA = """
if redis.call('get',KEYS[1])==ARGV[1] then
    return redis.call('del',KEYS[1])
else
    return 0
end
"""
```

## 亮点五：JWT 认证 + 多层权限体系

**文件**：`backend/app/core/security.py`、`backend/app/services/retrieval.py`

**核心问题**：企业知识库必须保证数据隔离——不同部门只能看到自己的文档，普通成员不能访问管理后台，管理员可以管理所有用户和权限。

### 认证流程

```text
注册/登录
    ↓
bcrypt 哈希密码（passlib）
    ↓
签发 JWT access_token (30min) + refresh_token (7天, HttpOnly cookie)
    ↓
后续请求携带 Authorization: Bearer <access_token>
    ↓
get_current_user 依赖注入:
  1. 解码 JWT，校验 exp/type/jti
  2. 检查 jti 是否在 Redis 黑名单（登出后失效）
  3. 查询用户是否存在且 is_active
    ↓
返回 User 对象给路由
```

### 权限模型

```text
三层权限（任一命中即可访问）:
├── 文档级: document_permissions (用户 ↔ 单个文档)
├── 数据源级: source_permissions (用户 ↔ 整个数据源)
└── 知识库级: knowledge_base_members (用户 ↔ 知识库)

角色:
├── admin: 管理后台全权限，检索无权限过滤
└── member: 只能检索有权限的文档
```

检索时，admin 跳过权限过滤，member 的 SQL 自动拼接 `PERM_FILTER` 子句。权限检查在数据库层完成，不存在"先查出再过滤"的数据泄露风险。

### Token 黑名单

登出时将 jti 写入 Redis 黑名单（TTL = token 剩余有效期），后续请求检查黑名单。Redis 不可用时安全优先，直接拒绝请求（503）。

## 亮点六：LangGraph Agent 编排

**文件**：`backend/app/agent_runtime/`

**核心问题**：复杂业务任务（如差旅报销审批）需要多步执行——查政策、查员工、查票据、校验、提交。单轮 LLM 对话无法保证执行顺序和数据一致性，需要 Agent 框架管理状态流转。

### 技术方案

```text
LangGraph StateGraph 状态图:

START → perceive → plan → tool_router → ┬→ tool_executor → reflect → ┬→ plan (循环)
                                         └→ finish → END               └→ finish → END

节点职责:
  perceive  — 初始化/恢复 AgentState
  plan      — RuleBasedPlanner 决定下一步动作
  tool_router — 路由: 需要调工具→executor, 完成→finish
  tool_executor — 调用工具，记录 observation
  reflect   — 检查: 是否完成? 是否超过 max_steps?
  finish    — 收尾: final_answer / clarify_question / failure_reason
```

### 循环安全

| 机制 | 作用 |
|------|------|
| `seen_actions` 去重 | 检测相同工具+相同参数的重复调用，立即终止 |
| `max_steps=8` | 防止无限循环 |
| `reflect` 节点 | 每步后检查是否该结束 |

### 当前限制（诚实声明）

Planner 使用 `RuleBasedPlanner`——基于正则和 if/elif 的规则引擎，不是 LLM function-calling 驱动。这意味着 Agent 只能处理预定义的差旅报销场景，无法泛化到任意任务。

选规则引擎的原因：优先保证 baseline 稳定。规则引擎可预测、可测试，不会产生 LLM 幻觉式规划。后续计划替换为 LLM 驱动的 Planner，届时 LangGraph 的条件边优势会更明显。

### 工具注册

```python
ToolRegistry 统一管理工具:
  search_policy      — 查询差旅报销政策
  get_employee       — 查询员工信息和审批关系
  list_receipts      — 查询员工票据
  validate_invoice   — 校验票据合规性
  submit_reimbursement — 提交报销申请
```

每个工具有 `required_args` 校验，调用失败返回 `ToolResult(status="error")` 而非抛异常，保证 Agent 不会因单个工具失败而崩溃。

## 亮点七：RAG 评测体系

**文件**：`backend/evals/`、`backend/app/api/v1/rag_evals.py`

**核心问题**：RAG 系统改了检索参数或 prompt 后，怎么知道是变好了还是变差了？没有评测就只能靠感觉调参。

### 评测维度

```text
1. 检索质量评测
   query → 期望命中的文档
   指标: Recall@k, MRR (Mean Reciprocal Rank)

2. 端到端评测
   query → 完整 RAG 回答
   评估: 回答是否基于检索文档、是否准确、是否完整

3. 回归检测
   当前评测结果 vs 历史基线
   指标退化 > 5% 标记为 regression
```

### 运行方式

```bash
cd backend
python -m evals.runner --dataset evals/datasets/travel_reimbursement.jsonl --out evals/reports/latest.json
```

### 核心指标

| 指标 | 含义 |
|------|------|
| `task_success_rate` | 任务状态是否符合预期 |
| `avg_steps` | 平均执行步数 |
| `tool_selection_accuracy` | 期望工具是否被正确选择 |
| `trajectory_score` | 轨迹是否无重复动作、无越权提交 |
| `avg_latency_ms` | 平均耗时 |

## 数据库设计

KnowFlow 使用 PostgreSQL + pgvector，业务数据和向量数据同库，享受事务一致性。

| 表 | 用途 | 关键字段 |
|----|------|---------|
| `documents` | 文档元数据 | title, content, status, kb_id, retry_count |
| `document_chunks` | 文档分块 | content, embedding(Vector), tsvector_content, metadata |
| `knowledge_bases` | 知识库 | name, rag_config |
| `knowledge_base_members` | 知识库成员 | kb_id, user_id |
| `conversations` | 对话 | user_id, title, goal |
| `messages` | 消息 | conversation_id, role, content, sources, rating |
| `users` | 用户 | email, name, role, is_active |
| `document_permissions` | 文档权限 | document_id, user_id |
| `agents` | Agent 配置 | name, system_prompt, knowledge_base_ids |

### 为什么选 pgvector 而不是 Milvus

| 维度 | pgvector | Milvus/Qdrant |
|------|----------|---------------|
| 事务一致性 | ✅ 文档、权限、向量在一个事务 | ❌ 需要双写同步 |
| 运维成本 | ✅ 复用现有 PostgreSQL | ❌ 额外服务 |
| 十万级 chunk 性能 | ✅ 够用 | ✅ 更快 |
| 千万级 chunk 性能 | ⚠️ HNSW 索引构建慢 | ✅ 原生优化 |
| 权限过滤 | ✅ SQL JOIN 直接过滤 | ⚠️ 需要元数据过滤 |

企业知识库通常文档量在十万级，pgvector 够用且运维成本最低。如果未来增长到千万级，再迁移到专用向量库。

```text
用户提问

  → RRF 融合 + 去重
  → LIKE 子串补充
  → Reranker 精排
