# KnowFlow 简历包装指南

本文档用于把 KnowFlow 项目包装成简历、面试和项目展示中可讲清楚的经历。所有内容基于真实代码实现，建议按真实情况描述，量化数据在跑过评测后补充。

包装重点：KnowFlow 已上线生产环境（know-flow.dev），有 392 个测试用例、完整前端、JWT 认证权限体系、Docker 全栈部署。这是区分"聊天 Demo"和"生产级 RAG 系统"的关键。

## 项目一句话描述

> KnowFlow 是企业级知识库 RAG 问答系统，已上线生产环境。核心实现双路混合检索（pgvector 向量 + BM25 全文）+ RRF 融合 + Reranker 精排的检索管线，支持 SSE 流式生成、Celery 异步索引、JWT 多层权限隔离和 LangGraph Agent 编排。

## 面试高频问题及回答思路

### Q1：为什么用双路检索 + RRF，不用单路向量检索？

**回答思路**

单路向量检索擅长语义匹配（"请假怎么请"能匹配到"年假申请流程"），但有两个致命问题：
1. 精确匹配差——搜员工姓名"赵六"，向量检索可能返回语义相近但不含"赵六"的结果。
2. 依赖 Embedding 服务——API 不可用时就完全瘫痪。

BM25 补了关键词精确命中，两路并行召回后用 RRF 融合。RRF 只用排名不用分数，公式 `1/(k+rank)`，天然消除向量 cosine（0-1）和 ts_rank（0-∞）的量纲差异，k=60 是论文推荐值，无需调参。

**可以补充**

还加了第三路 LIKE 子串补充：提取查询中的 CJK 连续片段做 ILIKE 模糊匹配，专门补回中文人名等向量/BM25 都漏掉的场景。这不是标准做法，是踩了实际检索的坑后加的。

### Q2：你的 RAG 检索效果怎么评估？

**回答思路**

项目有 `evals/` 评测模块，覆盖五个指标：Recall@k、MRR、task_success_rate、tool_selection_accuracy、trajectory_score。

检索质量用 Recall@k 和 MRR——准备 query + 期望命中的文档，跑检索看是否召回。端到端用 LLM 生成回答后人工或 LLM-as-Judge 评估。回归检测对比历史基线，退化超 5% 标记 regression。

**可以补充**

目前的限制是评测集还不够大，后续计划把用户反馈（thumbs up/down）自动回流到评测集，形成持续优化闭环。项目已有 feedback 模块和 rag_quality_issue 表做这件事。

### Q3：文档索引失败了怎么办？

**回答思路**

三层容错：

第一层，Celery 自动重试。索引任务 `max_retries=3`，失败后 re-raise 异常触发 `self.retry(countdown=60)`，间隔 60 秒重试 3 次。覆盖 API 限流、DB 连接闪断这类瞬时故障。

第二层，Beat 定时恢复。每小时扫描 `status='failed' AND retry_count < 3` 的文档，重置为 pending 重新入队。覆盖服务重启后卡在 failed 的持久故障。

第三层，状态安全。即使 commit 失败，也回滚后重新查询、重写 status，绝不卡在 processing。

**可以补充**

这个设计踩过坑——最初 `_index` 函数 catch 异常后不 re-raise，导致 `self.retry()` 从不触发，重试机制形同虚设。后来修复成失败后 re-raise 让 Celery 接管。

### Q4：SSE 流式输出怎么实现的？nginx 不会缓冲吗？

**回答思路**

后端用 FastAPI 的 `StreamingResponse` + `text/event-stream`，LLM 用 litellm 的 `stream=True` 逐 token 生成，后端 yield `data: {json}\n\n` 格式的 SSE 事件。

nginx 默认会缓冲响应，必须显式关闭：`proxy_buffering off` + `proxy_cache off` + `proxy_http_version 1.1`。后端响应头还加了 `X-Accel-Buffering: no` 双保险。

**可以补充**

难点是 prompt 要求 LLM 末尾输出 JSON（answer/sources/confidence），但流式时 JSON 片段不能显示给用户。解法是逐 token 累积，检测到 ` ```json` 或 `\n{` 边界后只累积不 yield，流结束后统一解析。

### Q5：权限隔离怎么做的？

**回答思路**

三层权限：文档级（document_permissions）、数据源级（source_permissions）、知识库级（knowledge_base_members），任一命中即可访问。

检索时 admin 跳过权限过滤，member 的 SQL 自动拼接 `PERM_FILTER`——三个 EXISTS 子查询。权限检查在数据库层完成，不存在"先查出再过滤"的数据泄露风险。

**可以补充**

JWT 双 Token：access 30min + refresh 7天 HttpOnly cookie。登出时 jti 写入 Redis 黑名单，后续请求检查黑名单。Redis 不可用时安全优先直接 503 拒绝。

### Q6：Agent 是真的 Agent 吗？Planner 怎么决策的？

**回答思路**

诚实说——当前 Planner 是规则引擎（RuleBasedPlanner），不是 LLM function-calling 驱动。用正则识别意图（如差旅报销），用 if/elif 决策工具调用顺序（先查政策→查员工→查票据→校验→提交）。

选规则引擎的原因是优先保证 baseline 稳定——可预测、可测试、不产生 LLM 幻觉式规划。LangGraph 的价值在于状态图编排和循环检测，后续替换为 LLM 驱动 Planner 时条件边优势会更明显。

**可以补充**

循环安全有三道：seen_actions 检测相同工具+参数的重复调用、max_steps=8 硬限制、reflect 节点每步检查是否该结束。工具调用失败返回 ToolResult(status="error") 而非抛异常，保证 Agent 不因单工具失败崩溃。

### Q7：为什么用 pgvector 不用 Milvus？

**回答思路**

pgvector 的优势是和业务数据同库——文档元数据、权限关系、向量在一个 PostgreSQL 事务里，不用维护两套数据一致性。企业知识库通常文档量在十万级，pgvector 够用。

劣势是千万级 chunk 时 HNSW 索引构建慢、召回延迟高，那时该迁移到 Milvus/Qdrant。但当前阶段，pgvector 的运维成本最低——不用多维护一个向量数据库服务。

**可以补充**

权限过滤也是一个原因。pgvector 可以直接 SQL JOIN document_permissions 做权限过滤，Milvus 需要用 metadata filter，灵活性和一致性都不如 SQL。

## 面试时的注意事项

- 讲双路检索时要强调 RRF 的"无参"优势——不用调权重，这是工程上的性价比选择。
- 讲 SSE 时要强调 nginx 缓冲这个坑——很多人不知道 nginx 默认会缓冲 SSE。
- 讲 Celery 重试时要诚实说踩过坑——最初异常被吞导致 retry 形同虚设，这是真实的 bug 经验。
- 讲 Agent 时要诚实界定——这是规则引擎驱动的 workflow，不是 autonomous agent，但用了 LangGraph 做状态编排。
- 讲 pgvector 选型时要给出迁移条件——十万级够用，千万级才需要 Milvus，说明你懂取舍。
- 讲权限时要强调"数据库层过滤"——不是查出结果再过滤，是 SQL 里就拼了权限子句。
